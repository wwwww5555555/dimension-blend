# 2026 融图新趋势 · 端侧可行性评估与落地记录

> 评估对象：需求清单「五、可选：引入 2026 年融图新趋势」的 4 项。
> 评估口径：**不破坏离线约束**（不调云 API、不上传、飞行模式全功能）。
> 结论分三类：**已落地并验证** / **可落地但需外部资源** / **端侧不可行（跳过）**。
>
> 事实核对时间：2026-10-16。所有论文数据来自公开摘要/官方页面，非推测。

---

## 0. 结论速览

| # | 趋势 | 判定 | 一句话理由 |
| --- | --- | --- | --- |
| 1 | 生成式光照先验（SHINE 思路） | ❌ **跳过** | 前提就是 FLUX/SD3.5 这类 12B 级扩散模型 + 多步隐空间优化，端侧差 2 个数量级 |
| 2 | 移动端轻量融合（MobileFusion / UHD-MFF） | ✅ **机制已落地**（两项） | 结构重参数化与 LUT 都是**纯工程机制**，无需训练即可实现并验证 |
| 2b | 同上（UHD-MFF 的 LUT 思路） | ✅ **已落地** | 三维查找表替代逐像素超越函数，实测有加速且数值等价 |
| 3 | 生成式光照估计（DiffusionLight-Turbo 思路） | ❌ **跳过** | SDXL+ControlNet+双 LoRA，官方 30 s/张（数据中心 GPU）；端侧无轻量替代 |
| 4 | 双轨制（低端经典 / 高端高配） | ✅ **已落地** | 设备档位 + 用户开关 + 管线如实上报，规则有单测钉住 |

**一句话总结**：4 项里 2 项不可行（都因为"生成式"这三个字直接绑定了十亿参数级模型），
另外 2 项被拆成**可验证的工程机制**落了地 —— 而且落地的是机制本身，不是"押注某个模型"。

## 1. SHINE 式生成式光照先验 → 跳过

**论文**：*Does FLUX Already Know How to Perform Physically Plausible Image Composition?*（SHINE），
arXiv:2509.21278，南洋理工 + 南京大学，2025-09。

**它的真实形态**（不是"一个轻量先验"）：
- 基座模型：**FLUX.1-dev**（12B）或 SD3.5；
- 需要 VLM 生成主体描述 → inpainting 模型补背景 → 单步正向扩散造初始噪声隐变量；
- 核心是 **Manifold-Steered Anchor loss：在去噪过程的每个时间步优化噪声隐变量**；
- 再叠 degradation-suppression guidance 与 adaptive background blending。

**量级对照**：

| 项 | SHINE 需要 | 本项目预算 |
| --- | --- | --- |
| 模型参数 | FLUX.1-dev 12B（fp16 ≈ 24GB，4bit 量化仍 ≈ 6–7GB） | 全部模型 ≤ 数百 MB |
| 峰值内存 | 数十 GB（含隐空间与优化器状态） | < 600MB（已放宽） |
| 单图耗时 | 多步扩散 + 每步隐变量优化，分钟级（数据中心 GPU） | 导出 < 5s |

**判定**：端侧不可行，**差距 2 个数量级**。而且要注意：SHINE 的**全部价值都来自那个生成式基座**——
把它"轻量化"之后就不再是 SHINE，而是另一个方法了。所以这里不是"先跳过、以后再补"，而是
**在"离线 + 手机"这个约束下这条路本身不成立**。

如果将来要在端侧做"生成式光照"，唯一有意义的形态是**训练一个小的判别式回归器**
（见第 3 节的替代路径），而不是把扩散模型塞进手机。

## 2. 移动端轻量融合 → 机制已落地

这一项是 4 项里**唯一真正端侧可行**的，因为它的核心是两个**纯工程机制**，
不依赖任何预训练权重：

### 2a. 结构重参数化（MobileFusion，ICML 2026）

**论文**：*MobileFusion: Mobile-Friendly Infrared and Visible Image Fusion via Structural Re-parameterization*，
ICML 2026（厦门大学），代码 `github.com/sucessfullys/MobileFusion`。

**论文的真实数据**：约 **4K（0.004M）参数**；Jetson Orin NX 上 **12.88 ms**（远低于 30fps 的 33ms 门槛）；
核心模块 RepMBConv 训练期用 5×5 / 3×3 / 1×3 / 3×1 / 1×1 **异构并行分支**，
推理期**数学等价地折叠成单个卷积**；论文的消融结论是"拼接 + 1×1 投影"显著优于"逐元素相加"。

**已落地**：`core-cv/src/main/java/com/naiwa/core/cv/fusion/RepConv.kt`
- `RepConv`：多分支（异构核）+ concat + 1×1 投影，`initDeterministic` 给确定性权重；
- `FoldedConv`：折叠后的单路径卷积，含 `effectiveKernelSize()`（外圈为零时自动收缩，省 64% 乘加）；
- `RepBlock`：`RepConv → PReLU → RepConv`，让"接入训练权重"这件事随时可做（激活必须夹在两个可折叠卷积之间）；
- **单测钉住核心主张**：`RepConvTest` 断言折叠前后逐点一致（相对误差 < 1e-4），
  并专门验证"只开 1×3 分支时折叠核只在中间一行非零"、"有效核自动收缩后结果不变"。

**用在哪**：`core-cv/.../fusion/RepDetailRefiner.kt` —— 一个**闭式设计**的多尺度高通算子
（`1×1 恒等 + 3×3 box + 5×5 box` 组合，折叠后 DC 增益严格为 0），
在 `EdgeHaloFix` 的过渡带上**把背景丢失的高频细节补回来**。

它修的是本项目已记录的真实缺陷（架构文档 §6.6）：泊松结果上采样后过渡带发糊。
因为 DC 增益为 0，所以**不改变整体亮度**；因为只在过渡带生效，所以中心区（纯融合）与掩膜外不受影响。

| 指标 | 值 |
| --- | --- |
| 参数量 | **52 个**（1 进 1 出、5 分支、单通道） |
| 折叠核 | 5×5 单路径（无 concat、无分支） |
| 折叠等价性 | 最大差值 **5.2e-08**（`RepConvTest`，随机权重下 4 分支全开） |
| `RepBlock`（带激活的折叠块） | 等价性 **2.4e-07** —— 将来接入需要非线性的训练权重时，折叠路径不用改 |
| DC 增益 | **7.3e-08**（严格为 0，不改变整体亮度） |
| `strength=0` | 返回 `null` 表示未执行，调用方退回原结果（不再逐像素跑一遍） |
| 边缘背景还原效果 | **8.91 → 4.86（下降 45%）** |

**修正权重的推导（第一版是错的，被测试抓回来）**

`band` 的取值必须满足一件事：**正比于"融合结果在多大程度上取代了羽化直贴"**。
第一版用了 `band = 1 - core`，直觉上是"过渡带就补偿"，但实测**把误差从 11.59 放大到 26.68** ——
因为在 `w ≈ 0` 的外圈，羽化直贴本来就保留了背景纹理，再补一遍就是**过冲**。

正确形式是两个因子的乘积：

```
band = smoothstep(core) × (1 - frogAlpha)
```

| 因子 | 含义 | 漏掉的后果 |
| --- | --- | --- |
| `smoothstep(core)` | 混合式里的 `w`：融合结果取代羽化直贴的比例 | 外圈重复补偿 → 过冲（实测 −133% 的"改进"） |
| `1 - frogAlpha` | 补偿只对**背景像素**成立 | 在奶蛙身上补背景细节 ＝ 污染奶蛙 |

两者相乘天然满足两条硬性质：**奶蛙本体（alpha=1）= 0**、**远离掩膜（w=0）= 0**，不需要额外门控。

**诚实的边界**：论文里"比现有方法更好"来自在 MSRS/FMB/LLVIP 上**训练**出来的权重，
本仓库**不提供未经验证的训练结果**。落地的写法让训练权重可以**原位替换**：
只要往 `RepDetailRefiner.repConv` 的权重数组里写入训练值，`fold()` 与调用方一行都不用改。
另外要注意**任务差异**：MobileFusion 是"红外 + 可见光同场景双输入"，
本项目是"单场景 + 抠好的前景"，因此它的权重不能直接搬用，必须重训。

### 2b. LUT 替代全分辨率重计算（UHD-MFF，ECCV 2026）

**论文**：*UHD-MFF: Shattering Barriers in Multi-Focus Ultra-High-Definition Image Fusion via Learnable Lookup Tables*，
ECCV 2026，arXiv:2606.31242，代码 `github.com/zyb5/UHD-MFF`。

**论文的真实数据**（官方性能表）：**0.0081M 参数**；RTX 3090 上 **11.03 ms / 4K → 90 fps**；
**GPU 峰值显存 1133 MB**；移动端（华为 P60 Pro / 骁龙 8+ Gen 1）**约 0.97 s**，
而对比方法里只有 SESF 能在手机上跑且要 **55.68 s**。

**能借鉴的核心**：**尺度解耦** —— 低分辨率空间做"区域级粗决策"，高分辨率只做"边缘级精修"，
用 LUT 查询 + 插值替掉全分辨率的重量计算。

**落地过程（含一次被实测否定的方案，这部分比结论更有价值）**

*第一版：三维点变换 LUT ❌*
用 33³ 三维查找表直接替掉整条 `sRGB ↔ Lab` 点变换，三线性插值。实测结果否定这个方案：

| 指标 | 结果 | 判断 |
| --- | --- | --- |
| 速度 | **0.80×**（比解析实现慢） | 三维三线性要 8 角点 × 3 通道 = 24 次读 + 24 次乘加 + 索引运算；解析实现只有 3 次 cbrt。省下的没赚回来 |
| 数值（sRGB→Lab） | 最大 ΔE76 = **1.14** | 网格步长 8/255，暗部精度不足 |
| 数值（Lab→sRGB 往返） | 最大通道误差 **32.8/255** | **结构性错误**：`gamma()` 在色域外会钳制到 0/255，插值跨越"钳制面"必然产生大误差 |

结论：**点变换不该用三维 LUT**。

*第二版：一维超越函数 LUT ✅（当前实现）*
真正贵的是 `f(t)=t^(1/3)`（每次 `rgbToLab` 三次 cbrt）与 `c^(1/2.4)`（每次 `labToRgb` 三次 pow）。
只把这两个函数换成 8192 / 4096 段的一维表：

- `core-cv/.../color/Lut1d.kt`：通用一维表（均匀网格 + 线性插值，越界**钳制而不外推**）；
- `core-cv/.../color/LabColor.kt`：`f()` / `gamma()` 走表，表内容由本文件的解析公式（`exactF` / `exactGamma`）生成；
- **只有一份数学实现** —— 表依赖公式，不存在两份实现漂移的问题（与 `KelvinRgb` 那次踩坑同一条原则）；
- `LabColor.useLuts` 开关 + `LabColorLutTest` 逐点比对查表版与解析版。

**实测**（`LabColorLutTest`，JVM 上跑，跨平台绝对值会变但量级关系稳定）：

| 指标 | 实测结果 |
| --- | --- |
| sRGB→Lab 数值等价（14.1 万采样点） | 最大 ΔE76 = **0.000606**（ΔL 0.000137） |
| Lab→sRGB 数值等价（1.39 万采样点） | 最大通道误差 = **0.0034 / 255** |
| **端到端产品输出等价**（整条颜色协调链路） | 最大通道差 = **0**、有差异的分量 **0 个** —— 优化对成品是**逐位无损**的 |
| 速度（40 万次 rgbToLab） | 解析 13.2 ms → 查表 **4.0 ms**，**加速 3.32×** |
| 建表耗时 | **4 ms**，进程内一次，计入 `FROG_PREP` 阶段计时，不混进 `COLOR_TRANSFER` |

对照第一版三维 LUT：ΔE76 从 1.14 降到 0.0006（**精度提升约 1900×**），
速度从 0.80× 变成 3.32×（**从更慢变成更快**）。

**注意 UHD-MFF 的可借鉴边界**：它的峰值显存 **1133 MB** 已经超过本项目放宽后的 600MB 预算，
而且任务是多焦点融合（同场景不同对焦的两张图），不是前景插入。
所以这里借鉴的是**思路**（LUT 替重算），不是它的模型或参数；
而且落到本项目的形态后，"哪一层用 LUT"必须重新实测 —— 上面的第一版就是反例。

## 3. 生成式光照估计 → 跳过；保留判别式替代路径

**论文**：*DiffusionLight-Turbo: Accelerated Light Probes for Free via Single-Pass Chrome Ball Inpainting*，
IEEE TPAMI 2026（arXiv:2507.01305）。

**它的真实形态与量级**：SDXL + depth 条件 ControlNet + Turbo LoRA + Exposure LoRA；
把"估计光照"重构成"补全铬球"；论文原文写明 **DiffusionLight 约 30 分钟/次，Turbo 版约 30 秒/次**（60× 加速）。
注意这 30 秒是**数据中心 GPU** 上的数字。

**判定**：端侧不可行。SDXL 的 UNet 本身约 2.6B 参数（fp16 ≈ 5GB），
再加 ControlNet 与两个 LoRA，**光加载就超过整个应用的内存预算**，更不用说 30s/张的耗时。

> **关于「Illumination Explorer」**：本轮公开检索**没有找到**与需求中描述一致的、可核对的论文条目，
> 因此不做编号与结论引用。但需求里这一项的本质是"用扩散模型做光照估计"，
> 其量级与 DiffusionLight-Turbo 属同一档，结论相同。

**端侧真正有意义的替代路径（现状说明）**：
`core-ai` 里**已经留好了判别式模型的槽位** —— `TfliteLightEstimator` + `ModelAssetInstaller`
（`GpuDelegate → XNNPACK CPU` 加速器链，模型缺失时静默回退纯 Kotlin 的传统 CV 估计器）。
缺的只有一件事：**训练权重**。这需要真实/合成的成对数据与训练流程，
本仓库不提供"没训过就塞进来"的模型，也不提供未经验证的训练脚本 —— 那是把不确定性伪装成功能。

**当前状态**：运行时光照估计走 `CvLightEstimator`（纯 Kotlin：灰度世界 + 白点法折中、
直方图分位、模糊后 Scharr 梯度场估方位、亮部质心估高度角、暗部交叉验证给置信度），
**功能完整**，只是精度低于训练好的模型。

## 4. 双轨制 → 已落地

**目标**：低端机走稳定路径，高配机可选更自然的高配路径，且飞行模式下两条都能用。

### 契约

`core-common/.../model/FusionBackend.kt`：

| 后端 | 含义 | 默认 |
| --- | --- | --- |
| `CLASSICAL` | 泊松 seamlessClone（档 1/2）+ 拉普拉斯多频段（档 3）+ α 加权回贴 | 所有设备可用 |
| `REP_DETAIL` | 在经典结果上加一步结构重参数化的**细节保真**修正 | 中/高端机默认开，低端机被否决 |

### 选路规则（`FusionTrack`，纯函数，有单测）

- **设备档位**（`DeviceCapabilityTier`）：`LOW_END` / `MID_RANGE` / `HIGH_END`
  - `LOW_END` = 厂商标记 `isLowRamDevice` ∨ 总 RAM < 4GB ∨ 核数 ≤ 4
  - `HIGH_END` = 总 RAM ≥ 8GB ∧ 核数 ≥ 8
  - **内存取不到（=0）必须不判为高端**（未知就按能力不足处理）—— 这条有专门单测
- **选路**：`低端机 → 无条件 CLASSICAL`；`中/高端 + 用户开关 → REP_DETAIL`
- **默认值**：用户设置缺省为**开**（"能上就上"），真正的门槛是设备档位而不是用户的默认设置
- **唯一判断点**：设备探测只在 `DeviceCapabilityProbe` 一处（`ActivityManager` 只在那一个文件里出现），
  避免"UI 说可用、管线说不行"的矛盾状态
- **如实上报**：`RenderResult.backend` + 编辑页状态行显示实际后端；管线只执行不判断

### UI

编辑页底部素材条新增「细节保真：开/关」，**仅在设备档位支持时渲染** ——
不给低端机用户一个"按了也没用"的按钮。ViewModel 里还有第二道防御：
即使 UI 被误触，低端机也不会跑上实验路径。

### 失败契约（集成加固）

细节保真是**增强**而不是主链路，因此它必须满足三条：

| 契约 | 实现 | 为什么必须这样 |
| --- | --- | --- |
| 失败不抛异常 | `RepDetailRefiner.refine` 参数不合法/区域为空时返回 **`null`**；`EdgeHaloFix` 再把 `try/catch` 兜一层 | 一个可选优化不能让预览或导出挂掉 |
| 失败不漏报 | `EdgeHaloFix.DetailReport` 带回 `applied` / `fallbackReason`；管线据此把 `RenderResult.backend` **从 `REP_DETAIL` 改回 `CLASSICAL`** 并打 warning | 否则会"功能没生效却照旧上报已启用"，那就是谎报 |
| 内存可控 | `band` 只在过渡带包围盒内分配（**区域局部坐标**），并按包围盒大小分配 | 整图 `FloatArray` 在 4096² 下要 **67MB**，而真正非零的只有一圈窄环 |

`strength = 0` 时直接返回 `null`（不执行），而不是逐像素跑一遍再返回等价结果 ——
这样"关闭"这条路径的代价是 0。

## 5. 性能预算放宽后的同步调整

本次同时把用户确认的新口径落到了代码（"600MB / 5s 不卡太死，能上就上"）：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 档位升级阈值 | 2500 ms | **3000 ms** |
| 档位超时线 | 4000 ms | **6000 ms**（不再按紧预算提前降级） |
| 低端机判定 | 分散在多处 | **收敛到 `FusionTrack.tierFor` 一处** |
| sRGB↔Lab 的 cbrt / pow | 逐像素超越函数 | **一维 LUT + 线性插值**（唯一真源仍是 `LabColor` 的解析公式） |

「超时档位进黑名单、只降不升」的防震荡机制保留不变 —— 预算放宽不会让震荡问题消失。

## 6. 明确未做的事（以及需要什么条件才能做）

| 项 | 现状 | 做下去需要 |
| --- | --- | --- |
| 训练一个真正的轻量融合网络（MobileFusion 形态） | 结构、折叠路径、闭式算子与测试都已就位；**权重未训练** | 成对数据（前景 + 场景 + 参考结果）与训练/导出环境；产出 `.tflite` 或直接写权重数组 |
| LiteRT 部署该网络 | 未做 | 需要真机验证推理正确性；本机无设备，交付未验证的原生推理路径风险大于收益 |
| 生成式光照先验 / 光照估计 | **判定不可行，不做** | 除非约束改变（允许云端、或允许 6GB+ 常驻模型 / 分钟级延迟） |
| GPU（GLES）加速融合 | 未做（沿用前一轮结论） | 真机上验证 EGL/GLSL 渲染正确性 |

**一句话**：能上的是**机制**，已经上了；没上的是**训练权重**与**真实设备验证**，
这两样都需要本环境之外的东西（数据、训练基础设施、真机），
我选择如实说明，而不是塞一个"看起来能用"的占位模型进来。
